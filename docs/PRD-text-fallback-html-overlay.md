# PRD: codex-image 텍스트 폴백 + HTML 오버레이 + 고해상도 재캡처

> **[폐기됨 — 2026-07-30]** 본 PRD의 HTML 오버레이·대화형 에디터·Chrome 재캡처 경로는 구현·실사용 후 폐기되었다. 사용성이 PPT 직접 작업보다 낮다는 사용자 평가에 따라, 폴백은 "텍스트 제외 배경 납품 + 라벨 가이드 표"로 단순화되었다 (SKILL.md §3-A 현행). 이 문서는 의사결정 이력 보존용으로만 남긴다.

## 1. 제품 개요

### 문서 정보
- 문서명: PRD-text-fallback-html-overlay
- 버전: v1.0 (2026-07-30)
- 대상: Claude Code 스킬 `codex-image` (경로: `~/.claude/skills/codex-image/`)

### 제품 요약
이 스킬은 현재 `codex exec`(비대화형 Codex CLI)로 gpt-image-2를 호출해 이미지를 생성하고, `review_server.py`의 핀-댓글 팝업으로 수정 루프를 돈다. 텍스트(한글 포함)는 프롬프트에 넣어 이미지에 직접 그리는 것이 현행 정책이지만, gpt-image-2의 한글 렌더링은 오탈자·글자 깨짐이 잦다 (SKILL.md 절대 규칙 및 7단계에 이미 "같은 한글 문구 2회 연속 깨지면 중단 후 대안 제안"으로 명문화되어 있음).

이번 업그레이드는 그 "대안"을 실제 기능으로 만든다. 한글이 깨졌을 때 사용자가 선택할 수 있는 **폴백 경로**를 추가한다: 같은 구도를 텍스트 전부 제외 버전으로 재생성하고(배경), 그 위에 HTML/CSS 오버레이(텍스트·라벨·박스)를 얹은 페이지를 Claude Code가 작성한 뒤, 헤드리스 브라우저로 고해상도 재캡처하여 최종 PNG를 산출한다.

과거에 PIL(Pillow) 기반 오버레이(`overlay_labels.py`)가 있었으나 합성 결과가 조잡하여 2026-07-30 사용자 지시로 전면 삭제되었다(git e490ce7). 본 PRD는 같은 실수를 반복하지 않기 위해 "왜 PIL이 실패했고 HTML은 무엇이 다른가"를 8장에서 냉정하게 검토한다.

## 2. 목표

### 비즈니스 목표
- 한글 텍스트가 필요한 이미지(포스터, 다이어그램, 발표자료 삽입 이미지)에서 재생성 반복으로 인한 ChatGPT Plus 구독 한도 낭비를 줄인다. 현재는 글자가 깨질 때마다 장당 1~2분 + 한도 1회를 소모하며 재생성하지만, 성공 보장이 없다.
- 텍스트 수정을 "재생성"에서 "HTML 편집 + 재캡처"로 전환하여, 문구 교체·오탈자 수정을 **한도 소모 0회, 수 초 내**에 처리한다.

### 사용자 목표
- 한글이 깨졌을 때 막다른 길("문구 단순화·영문 전환·텍스트 제거" 중 택일)이 아니라, 원하는 한글 문구를 100% 정확히 담은 최종 이미지를 얻는다.
- 기존과 동일한 핀-댓글 리뷰 UX로 오버레이 결과물까지 검수한다.

### Non-goals (하지 않을 것)
- **자동 레이아웃 AI 배치 엔진**: 라벨 위치·크기의 자동 최적화 알고리즘은 만들지 않는다. 배치는 Claude Code가 이미지를 보고 판단하며, 사용자가 핀 리뷰로 교정한다.
- **콜라주/다중 이미지 조립**: 기존 정책(그림 한 장 라벨링 전용, 콜라주 조립 금지) 유지.
- **WYSIWYG 오버레이 편집기**: review_server에 드래그 편집 UI를 넣지 않는다. 편집은 핀 댓글 → Claude가 HTML 수정으로 처리.
- **1차 생성 정책 변경**: "텍스트는 프롬프트에 포함해 함께 그린다"는 현행 기본 정책은 그대로 둔다. 폴백은 어디까지나 선택지다.

## 3. 사용자 페르소나

### 핵심 사용자 유형
단일 사용자 도구다. Claude Code를 Windows 11에서 사용하며 정부지원사업 문서·발표자료를 만드는 실무자 1인이 대상이다.

### 페르소나 상세
- **형일 (실무자)**: 발표자료·보고서에 들어갈 한글 라벨 포함 이미지(시스템 구성도, 배너, 포스터)를 자주 만든다. 디자인 감식안이 높아 "조잡한" 합성은 즉시 기각한다. 기술 세부사항보다 결과물 품질과 소요 시간에 민감하다.
- **Claude Code (실행 에이전트)**: SKILL.md 워크플로를 따르는 실행 주체. 프롬프트 작성, HTML 오버레이 작성, 캡처 실행, 검증을 수행한다.

### 역할 기반 접근
- 사용자: 폴백 진입 결정, 핀 리뷰, 최종 확정 권한.
- Claude Code: 생성·캡처·검증 실행. 파일 덮어쓰기 금지, 자동 재시도 1회 제한 등 기존 절대 규칙을 그대로 상속한다.
- 리뷰 서버: `127.0.0.1` 임의 포트에만 바인딩되는 1회성 로컬 서버(현행 코드 기준). 외부 노출 없음 — 이 보안 속성을 폴백에서도 유지한다.

## 5. 사용자 경험

### 진입점
- 자동 제안: 리뷰 팝업에서 텍스트 관련 핀이 반복되거나, 5단계 자가 검증에서 한글 깨짐이 발견됐을 때 Claude가 폴백을 제안한다.
- 명시 요청: 사용자가 처음부터 "글자는 오버레이로 얹어줘"라고 요청하면 1차 생성부터 텍스트 제외 버전으로 진행한다.

### 핵심 경험 (폴백 플로우)
```
[1차 생성: 텍스트 포함]           ← 현행 그대로
        │ 한글 깨짐 발견
        ▼
[폴백 제안 → 사용자 승인]          "재생성 vs 오버레이 폴백" 선택지 제시
        │
        ▼
[배경 재생성: no text]            codex exec -i 원본 (한도 1회 소모)
        │
        ▼
[overlay.html 작성]              Claude가 배경 위 % 좌표로 텍스트 배치
        │
        ▼
[고해상도 캡처 → final.png]       Chrome 헤드리스 CLI, 한도 소모 없음
        │
        ▼
[핀 리뷰 (기존 팝업 그대로)]
   ├─ 텍스트/라벨 핀 → HTML 수정 → 재캡처 (수 초, 무료)
   └─ 배경 핀       → codex 수정 (기존 7단계)
        │
        ▼
[확정 → 최종 보고]
```

### 고급 기능
- 문구만 바꾸는 재작업(예: 발표 직전 제목 변경)은 codex 없이 HTML 텍스트 교체 + 재캡처로 즉시 처리.
- 같은 배경에 다른 문구 세트를 얹은 변형본(국문/영문 버전 등)을 한도 소모 없이 여러 장 산출.

### UI/UX 하이라이트
- 리뷰 팝업 UI는 변경하지 않는다. 사용자 입장에서 폴백 여부와 무관하게 "핀 찍고 댓글 달기"라는 동일한 조작만 존재한다.
- 폴백 진입 시 비용을 명시 고지한다: "배경 재생성 1회(1~2분, 한도 차감), 이후 텍스트 수정은 무료·즉시."

## 6. 내러티브

형일은 발표자료용 시스템 구성도 이미지를 요청했고, 1차 생성 결과에서 "음장 센싱"이 "음장 센싱ㅇ"으로 깨진 것을 발견했다. 리뷰 팝업에 핀을 찍자 Claude가 "같은 문구가 또 깨질 확률이 높으니, 글자 없는 배경을 한 번만 재생성하고 텍스트는 HTML로 얹는 폴백"을 제안했다. 승인하자 2분 뒤 글자 없는 배경이 나왔고, Claude가 만든 오버레이 위에 정확한 한글 라벨이 얹힌 최종 PNG가 리뷰 팝업에 떴다. 라벨 하나가 장비를 가려서 핀으로 "이 라벨 오른쪽으로"라고 남기자, 이번엔 재생성 없이 몇 초 만에 수정본이 돌아왔다. 발표 전날 제목 문구가 바뀌었을 때도 이미지 재생성 없이 즉시 교체본을 받았다.

## 7. 성공 지표

### 사용자 중심
- 폴백 경로 최종 산출물의 한글 정확도 100% (HTML 텍스트는 렌더링 엔진이 그리므로 구조적으로 보장 — 측정은 캡처본 육안 검증).
- 텍스트 관련 수정 1회 소요 시간: 기존 1~2분(재생성) → 10초 이내(재캡처).

### 비즈니스(비용)
- 텍스트 수정으로 인한 codex 호출 횟수: 폴백 진입 후 0회 (배경 수정 제외).
- 한글 포함 이미지 1건 완성까지의 총 codex 호출: 평균 3회 이상(깨짐 반복) → 2회(원본 + 배경 재생성) 이하.

### 기술
- 최종 캡처 PNG 픽셀 크기 = 배경 원본 크기 (1:1, 자동 검증 가능).
- 캡처 파이프라인 성공률: Chrome 헤드리스 또는 resvg 중 하나로 95% 이상 (실패 시 FR-7 폴백 체인 작동).

## 8. 기능 3 기술 타당성 검토 (심층)

### 8.1 HTML → 고해상도 PNG 캡처 방법 비교

| 방법 | 설치 요구 | 해상도 제어 | 폰트 렌더링 | 자동화 난이도 | 판정 |
|---|---|---|---|---|---|
| Playwright Node 스크립트 (`chromium.launch` + `page.screenshot`) | `npm i playwright` + 브라우저 바이너리(~150MB). 단, Playwright MCP가 이미 설치돼 있어 Chromium 바이너리가 존재할 가능성 높음 | `deviceScaleFactor` 1~4 자유 지정, viewport 임의 크기, `fullPage`/요소 단위 캡처 | Chromium 엔진 — 시스템 폰트·웹폰트 완전 지원, `document.fonts.ready` 대기 가능 | 낮음. 20줄 내외 스크립트로 결정적(deterministic) 캡처: 로드 완료 → 폰트 대기 → 캡처 | **1순위** |
| Playwright MCP `browser_take_screenshot` | 이미 설치됨 | viewport 크기는 `browser_resize`로 제어 가능하나 deviceScaleFactor는 MCP 설정 고정 — 세밀 제어 불가 | 동일 (Chromium) | 도구 호출 몇 번으로 가능하나 해상도 재현성이 약함 | 보조 수단 (빠른 미리보기용) |
| Chrome 헤드리스 CLI (`chrome --headless=new --screenshot --window-size=WxH --force-device-scale-factor=N`) | 추가 설치 0 (Chrome 기설치) | window-size + scale-factor로 제어 가능. 다만 스케일 팩터 플래그는 headless 모드에서 버전에 따라 무시된 이력이 있어 결과 크기 검증 필수 | 동일 (Chromium) | 중간. 로딩 완료 시점 제어가 약함(`--virtual-time-budget`으로 보완). 원샷 CLI라 디버깅 어려움 | **2순위 (폴백)** |
| html2canvas | npm 패키지 + 결국 브라우저 자동화 필요 | canvas `scale` 옵션 | **실제 렌더링이 아님** — DOM을 JS로 다시 그리는 근사 구현. `backdrop-filter` 미지원, 그림자·블렌딩 부정확, 한글 자간·쉐이핑 어긋남 가능 | PNG를 파일로 빼내려면 어차피 Playwright 급 자동화가 필요 → 이중 비용 | **탈락** — 품질이 목적인 기능에서 "근사 렌더링"은 자기모순이고, 설치·자동화 비용도 더 든다 |

**해상도 상한과 1:1 규칙**: Chromium은 수천~1만 px대 캡처를 무리 없이 처리하므로 gpt-image-2 산출물(1K~4K) 범위에서 상한은 문제가 아니다. 진짜 함정은 **배경 업스케일**이다. viewport를 배경 원본보다 크게 잡거나 dSF를 곱해 배경 CSS 크기 × dSF > 원본 픽셀이 되면, 브라우저가 배경을 확대 보간해 캡처 전체가 물러진다. 따라서 규칙을 고정한다:

> **viewport CSS 크기 = 배경 원본 픽셀 ÷ deviceScaleFactor.**
> 예: 배경 2048×2048, dSF=2 → viewport 1024×1024. 결과 PNG는 2048×2048로 배경은 1:1 무손실, 텍스트·CSS 장식만 2x 선명도로 렌더링된다. 원본이 충분히 크면(2K+) dSF=1로 CSS 크기 = 원본 크기도 허용. **배경 확대는 어떤 경우에도 금지.**

### 8.2 배경 위 텍스트 배치 방식

배치는 단일 패턴으로 통일한다: 배경 이미지를 감싸는 wrapper에 `position:relative`, 모든 오버레이 요소는 `position:absolute; left:X%; top:Y%`.

- **% 좌표의 이점**: 해상도 독립적이라 dSF가 바뀌어도 좌표가 유효하고, 핀 리뷰 좌표계와 동일 규약이다(8.3절).
- **PIL 대비 스타일링 자유도**: PIL에서 직접 구현해야 했던 것들이 CSS 한 줄이다 — `text-shadow`(가독성 확보), `backdrop-filter: blur()`(반투명 유리 pill), `linear-gradient` 배경, `border-radius`, `letter-spacing`, 다중 폰트 굵기 위계. 특히 한글 조판(자간, 굵기별 힌팅, 서브픽셀 렌더링)은 브라우저 텍스트 엔진이 PIL의 `ImageDraw.text`와 비교 불가 수준으로 우수하다. PIL은 안티앨리어싱 품질과 자간 제어가 조악해 "포토샵 없이 그림판으로 쓴 글씨" 인상을 만드는 구조적 한계가 있었다.

### 8.3 핀 리뷰와의 좌표계 호환

**완전 호환이며, 이미 같은 코드 패턴이 존재한다.** `review_server.py`가 핀을 화면에 그릴 때 정확히 `d.style.left = p.x+'%'; d.style.top = p.y+'%'` (position:absolute, 이미지 wrapper 기준)를 쓴다. 서버가 반환하는 핀 JSON의 `x_pct`/`y_pct`(소수 1자리, 이미지 크기 대비 %)는 오버레이 HTML의 `left`/`top` 값으로 **변환 없이 그대로** 사용할 수 있다. 즉 "핀 3번(x 62.4%, y 18.0%): 여기에 제목"이라는 리뷰 결과를 `left:62.4%; top:18%`로 옮기면 사용자가 클릭한 바로 그 지점에 요소가 놓인다. 유일한 주의점은 앵커 기준(핀은 점, 텍스트 박스는 좌상단 모서리)이므로 중앙 정렬이 필요하면 `transform: translate(-50%,-50%)`를 병용한다.

### 8.4 PIL 오버레이 기각 원인의 극복 가능성 — 냉정한 평가

과거 기각 사유를 두 층으로 분해해야 정직한 평가가 된다.

**층 1 — 렌더링 품질 (도구의 문제, HTML이 실제로 극복함)**
- 불투명 단색 pill: PIL로 반투명·블러를 흉내내려면 크롭 → 블러 → 합성을 수동 구현해야 해서 사실상 불투명 사각형만 썼다. CSS `backdrop-filter: blur(12px)` + `rgba()` 배경은 이를 근본 해결한다.
- 글자 렌더링 조악: 위 8.2절 — 브라우저 텍스트 엔진으로 해결된다.
- 그림자·그라데이션 부재: CSS 기본기로 해결된다.
- 이 층에서는 **HTML 방식의 우위가 명확하고 검증 가능하다** (같은 라벨을 PIL/CSS로 나란히 렌더링하면 즉시 비교된다).

**층 2 — 레이아웃 설계 (설계자의 문제, 도구를 바꿔도 재발 가능)**
- "조잡함"의 절반은 배치 판단이었다: 라벨이 너무 많음, 크기 위계 부재, 피사체를 가리는 위치, 배경과 무관한 색. 이것은 PIL이 아니라 **배치를 결정한 쪽(Claude)의 디자인 판단 문제**이며, CSS로 갈아타도 판단이 나쁘면 "예쁘게 렌더링된 조잡한 레이아웃"이 나온다.
- 완화책(제거책이 아님을 명시한다):
  1. FR-9 스타일 프리셋 — 검증된 위계(제목 1 + 라벨 최대 4 + 캡션)와 색 규칙을 강제해 즉흥 디자인 변수를 줄인다.
  2. 배경 생성 프롬프트에 텍스트 자리 여백(negative space)을 명시적으로 확보시킨다.
  3. 오버레이 결과도 반드시 핀 리뷰를 거친다 — 수정 비용이 0에 가까우므로 리뷰 루프가 실질적 품질 게이트가 된다. PIL 시절에는 수정 1회가 재합성 스크립트 수정이라 루프가 무거웠다.
- **잔여 리스크**: 위 완화책으로도 첫 시안의 레이아웃 품질은 보장할 수 없다. 이 기능의 성패는 "첫 시안이 완벽한가"가 아니라 "수정 루프가 충분히 싸고 빠른가"에 걸려 있고, 후자는 구조적으로 확보된다(재캡처 수 초·무료).

### 8.5 폰트

- **기본**: 시스템 설치 맑은 고딕 — `font-family:'Malgun Gothic'`. 헤드리스 Chromium이 Windows 시스템 폰트를 그대로 쓰므로 네트워크 불필요, 실패 모드 없음.
- **권장 상위 옵션**: Pretendard. 두 가지 경로 — (a) CDN `@import`(jsdelivr): 간편하나 오프라인/네트워크 지연 시 실패, (b) 스킬 `assets/` 폴더에 가변 폰트 파일을 1회 내려받아 `@font-face` + 상대경로 참조: 이후 영구 무네트워크. **(b)를 권장**하되 MVP는 맑은 고딕만으로 출발해도 충분하다.
- 폰트 스택은 항상 `Pretendard, 'Malgun Gothic', sans-serif`로 폴백을 내장하고, 캡처 스크립트는 `document.fonts.ready` 대기(타임아웃 5초) 후 촬영한다 — 웹폰트 로딩 전 캡처로 폴백 폰트가 찍히는 사고를 방지.

### 8.6 산출물 파일 흐름

기존 명명 규칙(`gpt-image/YYYYMMDD-HHMMSS-<slug>.png`)을 확장한다:

```
gpt-image/
├── 20260730-141200-smart-home.png            # 1차 생성 (텍스트 포함, 깨짐)
├── 20260730-143000-smart-home-notext.png     # 배경 (텍스트 제외 재생성)
├── overlay-smart-home.html                   # 오버레이 소스 (재수정의 원본 — 보존 필수)
└── 20260730-143500-smart-home-final.png      # 최종 캡처 (배포용)
```

- HTML은 배경을 **상대경로**로 참조해 `gpt-image/` 폴더째 이동해도 열리게 한다.
- "기존 파일 덮어쓰기 금지" 규칙 상속: 재캡처는 새 타임스탬프 파일로 저장하고, HTML은 산출물이 아닌 소스로 간주해 in-place 수정을 허용한다(대신 최종 확정 시점의 HTML이 최종 PNG와 항상 일치해야 한다).
- 최종 보고에는 세 파일 경로를 모두 명시해, 이후 세션에서 "문구만 바꿔줘" 요청 시 HTML부터 찾게 한다.

### 8.7 캡처 스택 실측 확정 (2026-07-30 — HTML + Chrome 헤드리스 CLI 채택)

사용자 제안("생성 이미지의 SVG화 + 폰트 통일")을 GitHub 선행 도구 조사 + 동일 라벨 실측 렌더링으로 검증한 최종 결론:

- **트레이싱(진짜 벡터화)은 비채택**: visioncortex/vtracer(6,506★)가 photo 프리셋까지 제공하는 성숙 도구지만, 사진풍 이미지는 색 군집 포스터화로 원본 충실도가 깨진다. 정확한 한글 텍스트라는 목표에 벡터화 자체가 기여하지 않는다.
- **실측 비교(같은 라벨 3종, 1672×941 배경)**: SVG+resvg 0.6초 vs HTML+Chrome 헤드리스 CLI 1.5초 — 둘 다 1:1 출력·한글 정확. 그러나 SVG는 pill 자동 크기가 없어 폰트 실측 코드 60줄이 필요했고 실제로 박스 이탈 버그가 났다. HTML은 `padding`+`inline-block`으로 자동 해결(실측 코드 0줄), `backdrop-filter` 블러 가능, 수정 유연성 우위.
- **확정 체인**: **HTML 오버레이 + Chrome 헤드리스 CLI(1순위**, `--headless=new --screenshot --window-size=WxH --virtual-time-budget` — Playwright 불필요함이 실측 확인됨**)** → resvg SVG 오버레이(Chrome 부재 환경 폴백, linebender/resvg 단일 exe) → 사용자 브라우저 수동 확인. MVP 스크립트는 `scripts/capture_overlay.py`(Chrome 호출 + 1:1 크기 자동 검증 + selfcheck)로 구현 완료.
- **폰트 통일 전략(이질감 축소)**: gpt-image-2에 특정 폰트 강제는 불가능(모델에 폰트 개념 없음). 생성 프롬프트에 "clean geometric sans-serif typography" 류 스타일 유도를 넣어 모델이 그리는 영문·숫자의 인상을 맞추고, 오버레이 한글은 같은 계열 실폰트(맑은 고딕/Pretendard)를 쓴다.
- 이 절의 확정 내용이 8.1절 표의 사전 평가보다 우선한다 (8.1은 실측 전 문헌 비교).

## 9. 기술 고려사항

### 통합 지점
- SKILL.md 7단계(핀 수정)에 폴백 분기 추가, 신규 캡처 스크립트(`scripts/capture_overlay.py` — Chrome 헤드리스 호출 + 1:1 2중 검증, §8.7로 확정) 1개 추가. `review_server.py`는 **무수정 재사용**.
- 핀 처리 라우팅: 핀이 오버레이 요소 위인지 배경 위인지는 Claude가 HTML 소스의 요소 좌표와 대조해 판단한다(오버레이 요소 % 좌표를 알고 있으므로 계산 가능).

### 데이터 저장·프라이버시
- 전 과정 로컬. 리뷰 서버는 현행대로 `127.0.0.1` 임의 포트 1회성 바인딩, 외부 수신 없음. 웹폰트를 로컬 파일로 두면(8.5b) 캡처 단계도 완전 오프라인.
- 프롬프트에 비밀 정보 금지 등 기존 절대 규칙 전부 상속.

### 확장성·성능
- 캡처는 로컬 CPU 작업으로 수 초. 병목은 여전히 codex 생성(장당 1~2분)이며 폴백은 그 호출 횟수를 줄이는 방향이므로 성능은 순개선.

### 잠재적 과제
- "no text" 지시에도 gpt-image-2가 배경에 글자 비슷한 무늬를 그릴 수 있음 → 5단계 자가 검증에서 확인, 1회 재시도 규칙 적용.
- 텍스트 제외 재생성 시 구도가 원본과 달라질 수 있음(`-i` 첨부로 완화하나 완전 동일 보장은 없음) → 폴백 고지 시 이 한계를 함께 안내.

## 12. 마일스톤 및 순서

1인(Claude Code 세션) 작업 기준, 실코딩은 캡처 스크립트 1개 + SKILL.md 개정이 전부다.

- **Phase 1 — MVP (반나절)**: capture_overlay.py 작성 → 샘플 배경으로 1:1 해상도·한글 렌더링 검증 → SKILL.md 폴백 분기 반영. (2026-07-30 완료)
- **Phase 2 — 실전 1건 (1회 실사용)**: 실제 한글 깨짐 케이스에서 폴백 전 과정 수행, 사용자 확정까지. 여기서 나온 레이아웃 피드백을 프리셋(FR-9) 초안으로 기록.
- **Phase 3 — 보강 (필요 시)**: Chrome CLI 폴백, Pretendard 로컬 폰트, 프리셋 문서화.

## 13. 결론 및 권고

**조건부 타당 (조건 충족 시 진행 권고).**

- 렌더링 품질 층(8.4 층 1)에서 HTML/CSS가 PIL의 기각 사유를 실제로 극복한다는 점은 기술적으로 명확하다. 캡처 파이프라인(§8.7 확정: Chrome 헤드리스 CLI — 이미 설치, 추가 설치 0, Playwright 불필요)은 실측으로 1:1·한글 렌더링이 검증됐고, 핀 좌표계 호환은 기존 코드가 이미 증명한다. 텍스트 수정이 무료·즉시가 되는 비용 구조 개선도 실질적이다.
- 단, 조잡함의 나머지 절반인 레이아웃 판단(8.4 층 2)은 도구 교체로 해결되지 않는다. 따라서 다음 두 조건을 붙인다:
  1. **1:1 해상도 규칙과 캡처 크기 자동 검증을 MVP에 필수 포함**할 것 (업스케일 열화는 조잡함을 즉시 재현한다).
  2. **첫 실전 1건을 사용자 리뷰 게이트로 삼고**, 통과한 레이아웃만 프리셋으로 고정한 뒤 확대 적용할 것. 첫 건에서 레이아웃 품질이 리뷰 루프로도 수렴하지 않으면 이 기능은 폐기하고 "영문 전환·텍스트 제거" 현행 대안으로 회귀한다.

## 14. 유저 스토리

**US-001 — 폴백 진입 제안**
- 설명: 사용자로서, 한글이 깨진 이미지의 리뷰 중에 재생성 반복 대신 오버레이 폴백을 선택지로 제안받고 싶다.
- 인수 기준:
  - 같은 한글 문구가 2회 연속 깨지면 Claude가 폴백 선택지(재생성 계속 / 오버레이 폴백 / 문구 변경)를 제시한다.
  - 제안에는 예상 비용(배경 재생성 1회 한도 차감, 이후 텍스트 수정 무료)이 명시된다.
  - 사용자가 승인하기 전에는 폴백을 실행하지 않는다.

**US-002 — 처음부터 오버레이 방식 요청**
- 설명: 사용자로서, 처음부터 "글자는 오버레이로"라고 요청하면 1차 생성을 텍스트 제외 버전으로 진행하고 싶다.
- 인수 기준:
  - 요청 감지 시 텍스트 포함 1차 생성을 건너뛰고 배경 생성부터 시작한다.
  - 텍스트 포함 생성 대비 달라지는 점(구도 여백 확보)을 고지한다.

**US-003 — 텍스트 제외 배경 재생성**
- 설명: 사용자로서, 기존 이미지와 같은 구도의 텍스트 없는 배경을 얻고 싶다.
- 인수 기준:
  - 기존 이미지를 `-i`로 첨부하고 "keep composition identical" + "no text, no letters, no watermark"를 포함해 1회 생성한다.
  - 생성물은 새 파일(`-notext` slug)로 저장되고 원본은 보존된다.
  - 자가 검증에서 잔여 글자 무늬 여부를 확인해 보고한다.

**US-004 — 오버레이 HTML 생성**
- 설명: 사용자로서, 배경 위에 내가 요청한 정확한 한글 문구가 배치된 오버레이 페이지를 얻고 싶다.
- 인수 기준:
  - `overlay-<slug>.html`이 `gpt-image/`에 생성되고, 배경을 상대경로로 참조한다.
  - 모든 오버레이 요소는 absolute + % 좌표로 배치된다.
  - HTML 내 문구가 사용자 요청 문구와 자소 단위로 일치한다.
  - 브라우저에서 열면 추가 빌드 없이 그대로 렌더링된다.

**US-005 — 고해상도 1:1 캡처**
- 설명: 사용자로서, 배경 화질 손실 없이 오버레이가 합쳐진 최종 PNG를 얻고 싶다.
- 인수 기준:
  - 최종 PNG 픽셀 크기가 배경 원본과 동일하다 (스크립트가 자동 검증, 불일치 시 실패 처리).
  - 배경이 업스케일되지 않는다 (viewport CSS 크기 = 원본 ÷ dSF 규칙 적용).
  - 캡처는 폰트 로딩 완료(`document.fonts.ready`) 후 수행된다.

**US-006 — 최종본 핀 리뷰**
- 설명: 사용자로서, 캡처된 최종본을 기존과 동일한 핀-댓글 팝업으로 검수하고 싶다.
- 인수 기준:
  - 최종 PNG가 `review_server.py`에 인자로 전달되어 팝업이 뜬다.
  - 핀 JSON(`x_pct`/`y_pct`/`comment`) 파싱 및 확정/수정 분기가 기존 6단계와 동일하게 동작한다.

**US-007 — 오버레이 요소 핀 수정 (무료 루프)**
- 설명: 사용자로서, 라벨 위치·문구·크기에 대한 핀을 남기면 재생성 없이 빠르게 수정본을 받고 싶다.
- 인수 기준:
  - 오버레이 요소 위 핀은 HTML 수정 + 재캡처로 처리되며 codex를 호출하지 않는다.
  - 수정본은 새 타임스탬프 PNG로 저장되고 다시 리뷰 팝업에 오른다.
  - 핀의 `x_pct`/`y_pct`가 CSS `left`/`top` 값으로 그대로 반영된다.

**US-008 — 배경 요소 핀 수정**
- 설명: 사용자로서, 배경 자체의 문제(객체·색·조명)에 핀을 남기면 기존 방식대로 codex 수정을 받고 싶다.
- 인수 기준:
  - 배경 위 핀은 기존 7단계 `codex exec -i` 수정으로 라우팅된다.
  - 배경이 바뀌면 동일한 overlay HTML로 재캡처하여 최종본을 갱신한다.

**US-009 — HTML 소스 보존과 재사용**
- 설명: 사용자로서, 나중에 문구만 바꾼 변형본을 요청하면 이미지 재생성 없이 받고 싶다.
- 인수 기준:
  - 확정 시점의 overlay HTML이 `gpt-image/`에 남아 있고 최종 PNG와 내용이 일치한다.
  - 이후 세션에서 문구 변경 요청 시 HTML 수정 + 재캡처만으로 새 PNG가 산출된다.
  - 최종 보고에 배경 PNG·HTML·최종 PNG 세 경로가 모두 명시된다.

**US-010 — 캡처 엔진 폴백**
- 설명: 사용자로서, Chrome이 없는 환경에서도 폴백 기능이 동작하거나 최소한 명확한 안내를 받고 싶다. (§8.7 확정 체인 기준으로 개정)
- 인수 기준:
  - Chrome 부재 시 resvg SVG 오버레이로 폴백하고, 결과 크기를 동일하게 검증한다.
  - 둘 다 불가하면 HTML 경로를 알려주고 사용자 브라우저에서 여는 수동 절차를 안내한다.
  - 어느 엔진으로 캡처했는지 보고에 명시한다.

**US-011 — 폰트 실패 대응**
- 설명: 사용자로서, 웹폰트 로딩이 실패해도 한글이 깨지지 않은 결과물을 받고 싶다.
- 인수 기준:
  - 폰트 스택에 시스템 폰트(맑은 고딕) 폴백이 항상 포함된다.
  - 웹폰트 로딩 타임아웃(5초) 시 시스템 폰트로 캡처하고, 그 사실을 보고한다.
  - 어떤 경우에도 한글 자형이 누락(□) 렌더링되지 않는다.

**US-012 — 로컬 전용 보안 접근**
- 설명: 사용자로서, 리뷰·캡처 과정에서 내 이미지가 외부로 노출되지 않기를 원한다.
- 인수 기준:
  - 리뷰 서버는 `127.0.0.1` 임의 포트에만 바인딩되고 제출 1회 후 종료된다 (현행 동작 유지).
  - 캡처는 로컬 파일(`file://` 또는 로컬 서버)만 대상으로 하며 이미지가 외부 호스트로 전송되지 않는다.
  - 웹폰트를 CDN에서 받는 경우를 제외하면 전 과정이 오프라인에서 동작한다.

**US-013 — 폴백 실패 시 회귀**
- 설명: 사용자로서, 폴백 결과가 마음에 들지 않으면 언제든 기존 방식(재생성·문구 변경·텍스트 제거)으로 돌아가고 싶다.
- 인수 기준:
  - 폴백 진행 중에도 원본·1차 생성물이 모두 보존되어 있다.
  - 사용자가 회귀를 선택하면 폴백 산출물을 삭제하지 않고 기존 7단계 루프를 재개한다.
